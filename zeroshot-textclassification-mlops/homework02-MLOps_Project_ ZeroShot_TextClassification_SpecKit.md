## 1. Project Overview

Build a small, production-oriented zero-shot text classification platform using **Spec Kit**, **Hugging Face Transformers**, **Streamlit**, and **MinIO**.

The application must allow an administrator to download and manage zero-shot classification models, configure candidate labels, and allow users to classify text through a web interface. Every classification request must be saved to MinIO for later analysis.

The primary model should be:

```text
MoritzLaurer/deberta-v3-base-zeroshot-v2.0
```

The application must support at least **two zero-shot classification models**.

This project uses the corrected and recommended bucket name `zeroshot-learning-output`. The bucket name must remain configurable through an environment variable.

## 3. Functional Requirements

### 3.1 Model Management

Create an administrator page where an administrator can:

- View available zero-shot classification models.
- Select one or more models for download.
- Download models from Hugging Face.
- Save models into a local project directory.
- Display each model's download and availability status.
- Display the local model directory and cache location.
- Delete a selected downloaded model from local storage.
- Clear the Hugging Face cache when requested.
- Refresh the list of locally available models.
- View model identifiers and, when available, model revisions or versions.

The initial supported models should include:

```text
MoritzLaurer/deberta-v3-base-zeroshot-v2.0
facebook/bart-large-mnli
```

The design must make it easy to add more models through configuration rather than requiring major code changes.

Example model configuration:

```yaml
models:
  - id: MoritzLaurer/deberta-v3-base-zeroshot-v2.0
    name: DeBERTa Zero-Shot v2
    task: zero-shot-classification

  - id: facebook/bart-large-mnli
    name: BART MNLI
    task: zero-shot-classification
```

### 3.2 Model Download, Caching, and Deletion

The student must explicitly implement and document the model caching strategy.

The application must:

1. Check whether a model already exists locally.
2. Avoid downloading the model again when it is already available.
3. Download the model from Hugging Face when it is missing.
4. Store the model in a controlled directory, such as:

   ```text
   models/{model_id}
   ```

5. Allow the administrator to delete a selected local model.
6. Allow the administrator to clear the Hugging Face cache.
7. Handle incomplete or failed downloads safely.
8. Display meaningful success and error messages in Streamlit.
9. Prevent partially downloaded models from being treated as ready models.
10. Record the model identifier and revision used for inference whenever possible.

Example environment configuration:

```env
MODEL_DIR=./models
HF_HOME=./.cache/huggingface
TRANSFORMERS_CACHE=./.cache/huggingface/transformers
HF_TOKEN=
```

Downloaded model files, cache directories, and credentials must not be committed to Git.

### 3.3 Candidate Label Management

The administrator should be able to define or select candidate labels.

Example labels:

```text
sports
politics
technology
finance
health
education
```

The application should support:

- Adding labels.
- Removing labels.
- Saving a label set.
- Selecting a saved label set for inference.
- Validating that at least two candidate labels are provided.
- Preventing duplicate or empty labels.
- Persisting label configuration in a simple configuration file or another documented storage mechanism.

### 3.4 Text Classification Page

Create a separate user-facing Streamlit page where a user can:

- Enter or paste text.
- Select a downloaded zero-shot model.
- Select a candidate-label set.
- Submit the text for classification.
- View the predicted class.
- View the confidence score.
- View the ranked list of all candidate labels and scores.
- See the model used and the timestamp of the prediction.
- See an error message when no model or valid label set is available.

Example output:

```text
Input text:
The team won the championship after a very close game.

Predicted class:
sports

Confidence:
0.96

Ranked predictions:
1. sports — 0.96
2. education — 0.02
3. finance — 0.01
4. politics — 0.01
```

The classifier should use the Hugging Face zero-shot classification pipeline or an equivalent Transformers implementation.

### 3.5 MinIO Output Storage

Every successful classification request must be saved to MinIO.

Use the following default bucket name:

```text
zeroshot-learning-output
```

The application must create the bucket automatically if it does not exist.

Each stored result must include:

- Request ID.
- Input text.
- Predicted class.
- Confidence score.
- Candidate labels.
- Ranked labels and confidence scores.
- Model name and Hugging Face model identifier.
- Model version or revision, when available.
- Timestamp.
- Application version.
- Optional user or session identifier.
- Inference latency, if implemented.

Recommended MinIO object path:

```text
predictions/YYYY/MM/DD/{request_id}.json
```

Example JSON object:

```json

  "request_id": "6a6d6a85-9dbb-4f3e-9f89-5d8e4e8c1b2a",

  "predicted_class": "sports",
  "confidence": 0.96,

    "sports",
    "politics",
    "technology",
    "finance"
  ],
  "ranked_predictions": [
    {
      "label": "sports",
      "score": 0.96

    {
      "label": "technology",

    },

      "label": "finance",

      "label": "politics",
```

### 6.1 `constitution.md`

The Constitution defines the non-negotiable engineering principles and quality standards for the project. It is the highest-level project agreement and should guide all design and implementation decisions.

The Constitution should include:

- **Project purpose:** Build a reproducible zero-shot text-classification platform for learning MLOps practices.
- **Scope boundaries:** Define what is included in the first version and what is explicitly out of scope.
- **Reproducibility:** Dependencies, configuration, model identifiers, and model revisions must be documented and repeatable.
- **Configuration and secrets:** Credentials and environment-specific settings must come from environment variables or secret management; secrets must never be committed.
- **Model lifecycle management:** Models must be downloaded from Hugging Face, stored in a controlled local directory, reused when already available, and removable by an administrator.
- **Data persistence:** Every successful classification must be saved as structured JSON in the configured MinIO bucket.
- **Separation of concerns:** Streamlit UI, model management, inference, configuration, and MinIO storage must remain separate components.
- **Testing standards:** Core services require unit tests; MinIO integration behavior requires integration tests or documented test doubles.
- **Error handling:** Invalid input, unavailable models, failed downloads, and MinIO failures must produce clear errors without exposing secrets.
- **Observability:** Important operations such as model downloads, inference, cache cleanup, and MinIO writes must be logged with useful metadata.
- **Security and privacy:** Avoid logging sensitive input unnecessarily, do not expose credentials, and clearly document the limitations of local admin access.
- **Documentation:** Setup, usage, model caching, cache deletion, MinIO storage, testing, and troubleshooting must be documented.
- **Quality gates:** The project must pass formatting or lint checks, automated tests, and the acceptance criteria before it is considered complete.
- **Decision-record process:** Any deliberate exception to a constitutional principle must be documented with its reason and impact.
- **Programming language:** The project must always be implemented in Python. Other languages may be used only for supporting configuration, infrastructure, or deployment files, such as YAML, JSON, Dockerfiles, or shell scripts.

- **Deep-learning framework:** PyTorch must always be used as the deep-learning framework for model loading and inference. Other deep-learning frameworks must not be introduced unless an exception is formally documented and approved.

- **Object storage:** MinIO must always be used as the object-storage system for classification outputs. Prediction results must not be stored in alternative object-storage services or only on the local filesystem.

- **Storage contract:** Every successful classification result must be persisted as structured JSON in the configured MinIO bucket `zeroshot-learning-output`. Local files may be used for temporary processing, caching, or testing, but they must not replace MinIO as the system of record.

- **Technology consistency:** The implementation must use Python, PyTorch, Hugging Face Transformers, Streamlit, and MinIO as the standard technology stack for the first version. Any replacement or addition to this stack requires a documented architectural decision explaining the reason, benefits, risks, and impact on reproducibility.

- **Reproducible runtime:** The Python version, Python dependencies, PyTorch version, Transformers version, model identifiers, model revisions, and MinIO configuration must be pinned or documented clearly enough for another developer to reproduce the application.

- **Framework interoperability:** Hugging Face models may be loaded through the Transformers library, but inference must run using the PyTorch backend. The project must not silently switch to another backend.

- **Project purpose:** Build a reproducible Python-based zero-shot text-classification platform using PyTorch, Hugging Face Transformers, Streamlit, and MinIO for learning and demonstrating MLOps practices.

- **Data persistence:** Every successful classification must be saved as structured JSON in the configured MinIO bucket. MinIO is the mandatory object-storage system and the system of record for classification outputs. The default bucket name is `zeroshot-learning-output`.



The Constitution should also define how compliance is checked. For example:

- Every pull request or final submission runs the automated test suite.
- Configuration is loaded from environment variables or documented configuration files.
- No model artifacts, cache directories, `.env` files, or credentials are committed.
- At least one end-to-end test verifies that a prediction can be written to MinIO.
- The final README explains how a new developer can reproduce the project locally.

## 9. Security and Reliability Requirements

The student must:

- Never commit access keys, secret keys, Hugging Face tokens, or `.env` files.
- Use `.env.example` with placeholder values only.
- Validate and sanitize user input.
- Avoid logging sensitive credentials or tokens.

- Handle MinIO connection failures with a clear user-facing message.
